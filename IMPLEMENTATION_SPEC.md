# Техническое задание для Codex: гибридный интеллектуальный ассистент по юриспруденции

**Статус:** спецификация для самостоятельной реализации в новом репозитории.  
**Версия:** 1.0, 28.10.2026  
**Тема курсовой:** «Гибридный интеллектуальный ассистент по юриспруденции с нейросетевой обработкой естественно-языковых запросов».  
**Исполнитель:** Codex, работающий в терминале VS Code / PyCharm.  
**ОС разработчика:** Windows; запуск Linux-компонентов через Docker Desktop + WSL2.  
**Ограничение:** только бесплатные локальные компоненты; никакой платной LLM API, платной БД или облачной инфраструктуры.

> **Главный критерий:** пользователь работает с единым сайтом, его юридический запрос обрабатывается локальной LLM, реальная юридическая база знаний остаётся в **OSTIS/sc-machine**, а результаты приходят из действительного запроса к ней или из существующего решателя. Нельзя выдавать фальшивый ответ, локальный JSON со статьями или SQLite за интеграцию с OSTIS.

## 2. Цель и рамки

Сделать **отдельный монорепозиторий** с единым пользовательским сайтом на Python, реальным OSTIS/sc-machine, локальной нейросетевой обработкой русских юридических запросов и **одним локальным запуском на Windows после первоначальной установки**.

**Допускается:** новый Python backend и собственная HTML/Jinja-верстка вместо копирования старого приложения; SQLite для пользователей, истории и форума; Docker для sc-machine и Ollama; Python/SC-шаблоны вместо отдельных старых агентов при сохранении результатов.

**Не допускается:** подменять SC-память обычным словарём/SQLite/набором статических JSON; считать простую генерацию LLM «решением OSTIS»; удалять страницы ради демонстрационного чата; требовать платный API; утверждать, что движок OSTIS реализован на Python.

**Результат:** `start.bat` поднимает подготовленную систему без ручного переключения ОС или нескольких терминалов. `setup.bat` выполняет первичную сборку базы и загрузку модели — это отдельная операция и может занимать значительное время; её не следует повторять без необходимости. `stop.bat` штатно останавливает сервисы, не удаляя данные.

## 3. Целевая архитектура

```text
Браузер (Windows)  http://localhost:5000
              │
              ▼
       Python Web App (Flask)
       ├─ Web UI (Jinja + HTML/CSS/JS)
       ├─ Account / forum / calendar / history → SQLite
       ├─ Legal search orchestrator
       │    ├─ Baseline NLP (поиск терминов без LLM)
       │    ├─ LLM interpreter → Ollama (локально)
       │    ├─ Entity / concept linker (проверка по реальной OSTIS KB)
       │    └─ OSTIS gateway → sc-server WebSocket
       └─ Evidence-based answer builder
                                │
                                ▼
                       sc-machine 0.10.x
                       ├─ SC-база знаний
                       ├─ SC-шаблоны
                       └─ доступные агенты / решатель
```

**Отделение обязанностей:**
- SQLite: пользовательские данные и транзакционные функции сайта; это не юридическая база знаний.
- OSTIS: юридические сущности, тексты, связи, SC-адреса, семантический поиск и действительные агенты.
- LLM: только извлечение намерения, ключевых терминов, контекста и возможное перефразирование **уже подтверждённых** результатов. Ни одного самостоятельного утверждения о норме права.
- Python orchestrator: маршрутизация, форматирование, проверка терминов и взаимодействие с SC-клиентом.

### Предпочитаемые технологии

- Python **3.11** для приложения и тестов.
- Flask + Jinja2 + WTForms/Flask-WTF; Flask-Login; SQLAlchemy + Alembic/Flask-Migrate; Pydantic 2 для схем; `httpx` или `requests` для Ollama.
- `py-sc-client==0.4.0`, `py-sc-kpm==0.4.0` как исходно совместимая пара с `sc-machine 0.10.0`. Изменять версии только после реальных интеграционных тестов.
- SQLite (файл в постоянном Docker-volume). Установить `PRAGMA foreign_keys=ON`, миграции схем.
- pytest, pytest-cov, ruff; Playwright опционально для реального браузерного smoke.
- Docker Desktop + WSL2 с Linux containers; ОС не должна требовать native CMake/Conan.
- Ollama (предпочтительно отдельный контейнер с постоянным volume; резервно Windows-хост через `host.docker.internal`). Начальная модель: **`qwen3:4b-instruct`** (~2.5 ГБ в Ollama). Модель настраивается через `OLLAMA_MODEL`, не привязывать код к ней. Веса скачиваются только при явной первичной установке.
- Python-код не должен зависеть от GPU: CPU-режим допустим с предупреждением о скорости; GPU в Docker на Windows — отдельная оптимизация после работоспособности на CPU.

## 4. Обязательная функциональность сайта (матрица совместимости)

Сначала создай `docs/PARITY_MATRIX.md`: на каждую функцию укажи исходный маршрут, используемые данные/агент, новый маршрут, статус миграции и тест. Прототип старого сайта — ориентир для поведения, а не требование дословно скопировать внешний вид.

| Гостевой режим | просмотр открытых разделов, поиск без изменения приватных данных | Flask/сессия |

| Профиль и настройки | просмотр и редактирование собственных данных | SQLite |
| Юридические запросы | текстовый ввод, классический режим и LLM-режим, реальные результаты OSTIS | **OSTIS** |
| Справочник | поиск понятий по SC-базе, переход к связанным элементам | **OSTIS** |
| Просмотр статьи/акта | текст, название, идентификатор, ссылки на источник, если имеются | **OSTIS/исходные SC/HTML** |
| Личный кабинет | история запросов, заметки, закладки, настройки | SQLite |
| Календарь | список, добавление и удаление личных событий | SQLite |
| Форум | темы, сообщения, редактирование/удаление своих сообщений, оценки/поиск | SQLite |
| Тестирование | вопросы и проверка ответов с реальным источником; не имитировать неизвестные ответы | по возможности **OSTIS** |
| Шаблоны документов | каталог шаблонов, открытие/заполнение предусмотренных исходной системой форм | локальные данные с источниками |

- Не убирать пункт из меню потому, что трудно перенести. Реализовать поэтапно и помечать незавершённое в `STATUS.md`, но **в финальном релизе все строки выше должны проходить проверки**.

- Для ссылок на статьи показывать, какая редакция правового текста доступна. Не заявлять актуальность законодательства без проверки даты/источника.

## 5. Контракт нейросетевого модуля

### Сценарий

```text
1. Пользователь вводит запрос на русском языке.
2. Flask проверяет длину запроса и выбранный режим.
3. Baseline: лексическая обработка/поиск терминов.
   LLM: локальная модель возвращает JSON со смыслом запроса и терминами.
4. Pydantic валидирует JSON; отсутствующие факты остаются null/[] (запрещено додумывать).
5. Entity linker проверяет кандидатов в существующей OSTIS KB.
6. Gateway выполняет действительный вызов поиска/агента.
7. Собирается список подтверждённых источников, SC-идентификаторов и выдержек.
8. Сайт показывает подтверждённый результат; LLM может перефразировать его, но не добавлять нормы.
9. Если OSTIS недоступен/ничего не найдено — честная ошибка или "нет подтверждённого ответа".
```

### Схема результата интерпретации

Точная Pydantic-модель может быть расширена, но минимум:

```json
{
  "intent": "find_legal_information",
  "domain_hints": ["трудовое право"],
  "search_terms": ["трудовой договор", "увольнение"],
  "entities": [
    {"name": "работник", "type": "participant", "original_text": "меня"}
  ],
  "facts": [
    {"key": "event", "value": "увольнение", "present_in_user_text": true}
  ],
  "missing_information": [],
  "needs_clarification": false
}
```

`domain_hints` — гипотезы модели, **не подтверждённые юридические классификации**. Содержимое каждого поля проверяется. Для значений, которых нет в исходном запросе, `present_in_user_text=false` и они не должны передаваться как факт.

Вызов Ollama локальный: `POST /api/chat` c `stream=false` и `format=<JSON Schema>`. После ответа — `model_validate_json`, таймаут, ограниченное число повторов, отсутствие молчаливого отката к неподтверждённому ответу. Поскольку структурированный вывод ограничивает **формат**, а не истинность фактов, каждый термин обязательно сопоставлять с реальной KB.

### HTTP-контракт собственной API

Реализовать эндпоинты:

- `GET /health/live` → процесс работает (без зависимости от OSTIS/LLM).
- `GET /health/ready` → отдельные статусы `database`, `ostis`, `llm`; вернуть 503 при критической неготовности; не раскрывать секреты.
- `POST /api/legal/query` → `{"query":"...","mode":"baseline|llm"}`.
- `GET /api/legal/concepts?term=...` → подтверждённый поиск понятий в OSTIS.
- `GET /api/legal/sources/<id>` → просмотр источника только при реальной доступности.

Пример ответа на запрос:

```json
{
  "query": "Что такое трудовой договор?",
  "mode": "llm",
  "interpretation": {
    "intent": "definition",
    "search_terms": ["трудовой договор"],
    "domain_hints": ["трудовое право"]
  },
  "matches": [
    {
      "source_system": "ostis",
      "sc_identifier": "example-from-real-kb",
      "title": "Подтверждённое название",
      "excerpt": "Текст, полученный из базы знаний",
      "source_document": null
    }
  ],
  "answer": {
    "text": "Краткий ответ, составленный только из найденных сведений",
    "status": "grounded"
  },
  "runtime": {"ostis_connected": true, "llm_used": true, "mock": false}
}
```

`example-from-real-kb` и другие строки в примере — **образцы формата**, не настоящие идентификаторы. Реальное приложение обязано подставлять обнаруженные SC-ID, **не оставлять эти заглушки**. При пустом результате `matches=[]`, `answer.status="no_evidence"`, ответ без юридических утверждений.

### Поведение при сбоях

- Нет Ollama → понятная ошибка в LLM-режиме и предложение перейти на `baseline`, **без автопереключения без уведомления**.
- Нет OSTIS → не выводить «юридический ответ» из одной LLM; показать 503/сообщение и логи.
- JSON модели некорректен → повторить ограниченно 1 раз, затем вывести ошибку формата.
- Термин не сопоставился → не придумывать SC-адрес; показать `unmatched_terms`.
- Таймаут/разрыв WebSocket → bounded retry, корреляция по request_id, понятный статус.
- Неавторизованный POST к приватным данным → 401/403, никакой утечки пользовательских данных.
- Пустые ответы, большие запросы, HTML в строке, SQL-инъекция и prompt injection → тесты негативных сценариев.

## 6. Реальная интеграция с OSTIS

**Это обязательная часть и главный технический риск.**

1. На первом этапе переиспользуй исходную конфигурацию `sc-machine 0.10.0`, SC-базу и нужные агенты. Проверь `repo.path`, монтирование директорий в контейнер, расширения, WebSocket `ws://machine:8090/ws_json` внутри Docker-сети.
2. Реализуй слой `OstisClient` для соединения, поиска SC-понятий/связей/текстов, получения статуса, корректного закрытия соединения. В Python не используется `localhost` для другого контейнера; применять имя службы Compose `machine`.
3. Выполни живой smoke-тест **по реальному** термину из KB. Сохрани в `docs/TEST_REPORT.md`: ввод, тип SC-запроса/имя агента, найденный SC-ID, источник, итог. Не считать `connect()` достаточной проверкой интеграции.
4. Реализуй `OstisGateway` поверх стабильного публичного интерфейса. Первый путь — текущий `action_user_request`, альтернативный — SC-template search. Не добавляй новый SC-action, пока не подтверждено, что старого недостаточно.
5. Для агента учти протокол действия: SC-link + `rrel_1` + action class + `action_initiated` + ожидание `action_finished_*` + чтение `nrel_result`. Подтверди имена ключевых узлов на ревизии 0.10.0 и содержимое фактической KB. Не переписывай API по догадкам.
6. Не копируй из оригинального `service/agents/ostis.py` глобальные `payload` и `callback_event` без изменения: при одновременных запросах ответы могут смешиваться. Сделай request-scoped state, correlation ID и защищённый lifecycle подписок. Если используемая версия SDK не поддерживает безопасную параллельность, явно сериализуй вызовы с lock и тестируй это.
7. Для юридических выводов сохраняй цепочку происхождения: термины → SC-элементы/ссылки → статьи/текст → итог. Не маскируй простую строковую выдачу под полноценное доказательство.
8. Испытай гипотезу о `linkAddrs1.size() > 1` в `user_request_agent.cpp`: отдельный тест случая с ровно одним найденным термином. Исправлять **только** при подтверждённой ошибке и с регрессионным тестом.
9. Если какие-то C++-агенты нужны исключительно для регистрации/форума/календаря, можно заменить функциональность Python + SQLite после тестового подтверждения полной эквивалентности. Юридические агенты оставлять до завершения реального E2E.
10. `sc-web` сохраняй как необязательный debug-интерфейс (Compose profile или отдельная служба): основной сайт — Flask; не надо показывать пользователю два разных входа.

## 7. Docker и локальный запуск на Windows

**Целевая установка:** Docker Desktop (Linux containers/WSL2), Git, Python 3.11 для необязательного локального запуска backend, и достаточно места для моделей и KB. Docker Desktop работает на поддерживаемых редакциях Windows 10/11 при выполнении требований WSL2. Пожалуйста, проверяй реальную ОС/редакцию перед установкой.

### Compose

- `machine`: оставить подход upstream, исходная KB и расширения из рабочего Dockerfile, порт 8090 доступен Python-контейнеру. `healthcheck` обязателен.
- `app`: Flask-сервер на 5000, конфигурация и парольные секреты из environment, постоянная БД, `depends_on` + собственные retries при старте.
- `ollama`: локальный сервер на 11434 с отдельным постоянным volume. Запрос из Flask на `http://ollama:11434`. Не закачивать модель при каждом старте.
- `sc-web`: опциональный debug-профиль, если требуется преподавателю или отладке.
- Все порты, открываемые хосту, по умолчанию связать с `127.0.0.1` (локальный доступ), где Docker это поддерживает. Внутри сети связь по именам служб.
- Не делать Docker Compose `down -v` в `stop.bat`; запрещено удалять тома без отдельного действия и подтверждения.

### Файлы запуска

- `setup.bat`: проверяет Docker/WSL2, сообщает о недостающих зависимостях, клонирование source разрешённых зависимостей/инициализация submodules, сборка контейнеров, формирование исходной KB, инициализация DB/migrations и скачивание модели `OLLAMA_MODEL`. Не обещай полное offline при первой установке: исходники/образы/веса требуют сети.
- `start.bat`: проверяет готовность Docker Desktop, запускает контейнеры через Compose, ожидает healthy/ready с конечным timeout, открывает `http://localhost:5000`.
- `stop.bat`: штатный `docker compose stop`, сохранение БД и KB.
- `rebuild-kb.bat`: **ручная** пересборка KB только после явного подтверждения/бэкапа.
- `README.md`: пошаговая инструкция для Windows PowerShell/CMD и для Linux, команды отладки `docker compose logs`, проверки GPU необязательны.

### Конфигурация `.env.example`

```dotenv
APP_ENV=development
APP_PORT=5000
SECRET_KEY=CHANGE_ME_LOCALLY
DATABASE_URL=sqlite:////app/data/app.sqlite3
OSTIS_WS_URL=ws://machine:8090/ws_json
OLLAMA_BASE_URL=http://ollama:11434
OLLAMA_MODEL=qwen3:4b-instruct
OLLAMA_TIMEOUT_SECONDS=120
MAX_QUERY_LENGTH=1500
LEGAL_QUERY_DEFAULT_MODE=baseline
```

Реальный `.env` игнорировать в Git; `SECRET_KEY` генерировать локально на `setup.bat`/в скрипте подготовки. Пароли — только через современное хеширование; никаких паролей в базе в открытом виде. Если подтверждение электронной почты невозможно офлайн, сделать **явный dev-режим** с локальным одноразовым кодом и оформить это как ограничение, не изображать отправку реальной почты.

## 9. Этапы реализации и контрольные точки

### S0 — аудит (обязательно первым)

Результат: `docs/REPO_AUDIT.md`, `docs/PARITY_MATRIX.md`, зафиксированные SHA upstream, проверка лицензий, список реально используемых сервисов/агентов и SC-онтологий, Windows prerequisites, список известных рисков. Отдельно проверить, какие модели/темы доступны в KB и какой вызов возвращает связанные статьи.

**Gate S0:** нет непроверенных гипотез, записанных как факты; схема зависимостей и приоритеты миграции зафиксированы.

### S1 — инфраструктура

Перенести разрешённые upstream-компоненты OSTIS в новый репозиторий или подключить как pin/submodule; воспроизводимый Docker build, сборка KB и запуск `sc-machine`; healthchecks, `.env.example`, `setup.bat`, `start.bat`, `stop.bat`.

**Gate S1:** на Windows или Linux с Docker `sc-machine` действительно запускается и отвечает на WebSocket; KB собрана. Если Windows сейчас недоступен, отметить `Windows: NOT TESTED`, не выдавать как проверенное.

### S2 — Python-backend + живой OSTIS

Flask application factory, конфигурация, регистрация blueprint-ов, клиент OSTIS, обработка исключений; сначала страница `/requests` и справочник `/directory`. Тестовые сценарии из фактической KB.

**Gate S2:** `GET /health/ready` подтверждает реальный OSTIS, а пользователь получает не пустой результат по реально существующему SC-термину. Для каждого результата доступен его источник.

### S3 — локальная LLM и сравнение с baseline

Ollama в Compose, schema-constrained output, валидатор, нормализация, linking с SC-классами, endpoint `/api/legal/query`, переключатель режима, отображение источников. Не менять OSTIS-контракт для первого успешного вертикального сценария.

**Gate S3:** свободный русскоязычный запрос проходит `Flask → Ollama → JSON → OSTIS → подтверждённый результат`; при выключенном Ollama baseline продолжает работать; при выключенном OSTIS нет «юридического» ответа.

### S4 — страницы и пользовательские данные

Регистрация/авторизация, профиль/настройки, история, закладки, заметки, календарь, гостевой режим. SQLite, миграции, тесты прав доступа.

**Gate S4:** пользователь А не видит и не меняет данные пользователя Б; все страницы доступны из меню; данные сохраняются после перезапуска контейнеров.

### S5 — дополнительные функции

Форум, тестирование, шаблоны, новости и кеш, страницы нормативных статей; здесь при необходимости использовать уже написанную логику или собственную, но без слепого копирования кода при неясной лицензии.

**Gate S5:** все пункты `PARITY_MATRIX` реализованы и проверены; ни один исходный пользовательский сценарий не исчез без документированного согласованного исключения.

### S6 — оценка качества и надёжности

Датасет из **не менее 30** русскоязычных запросов по действительно представленным областям KB. Для каждого теста разметить ожидаемые термины/понятия, ожидаемые ссылки на SC-объекты, «недостаточно данных» или «нет совпадения». Сравнить baseline и LLM на одном наборе. Показать precision/recall/F1 по извлечению терминов, долю найденных реальных SC-объектов, долю ошибочных/неподтверждённых ссылок, время ответа p50/p95 и частоту таймаутов. Если метрика не применима, обосновать замену и не придумывать цифры.

**Gate S6:** `docs/TEST_REPORT.md` с методикой, реальными результатами, конфигурацией модели/ОС и ограничениями. Unit-тесты с моками отделены от E2E на реальном OSTIS.

### S7 — окончательная сборка и демонстрация

README с инструкцией для проверяющего, итоговая архитектура, описание сохранённых/заменённых компонентов и лицензий, `.env.example`, тесты, подготовленные скриншоты только с реального запуска, список известных ограничений.

**Gate S7:** свежий клон + первичная установка + запуск работает в целевой Windows-среде; если на текущем устройстве проверить не удалось — прямо записать это в отчёт, не подменять выводом «должно работать».

### Особенность второй опроцентовки

Для **второй опроцентовки** главный промежуточный результат — выполнение S0–S2 и по возможности части S3: схема архитектуры, обоснованный выбор технологий, рабочий OSTIS и начальная обработка запроса через Python. **Полный объём S4–S7 относится к дальнейшей реализации**, но не отменяется из общего задания.

## 10. Проверки и команды

Codex сам определяет корректные команды по созданной структуре, но поддерживает минимум:

```bash
# без подключения внешних сервисов — быстрая статическая и unit-проверка
python -m pytest backend/tests/unit -q
python -m ruff check backend

# инфраструктура
# docker compose config
# docker compose build
# docker compose up -d
# docker compose ps
# docker compose logs --no-color --tail=100

# реальные интеграционные тесты, только при запущенной KB/LLM
# python -m pytest backend/tests/integration -m live_ostis -q
# python -m pytest backend/tests/e2e -m live_stack -q
```

Обязательно реализовать fixtures с явным разделением `mock`/`live`; случайный сетевой недоступный сервер не должен превращаться в `PASS`. CI может пропускать live-тесты с меткой `SKIPPED`, но итоговая приёмка S3/S7 их требует.

**Сценарии для тестирования:**

1. Действительное SC-понятие (точное название) находится в базе; ссылка на источник не выдумана.
2. Разговорное перефразирование известного понятия успешно сопоставлено либо честно не распознано.
3. Незнакомый термин не создаёт поддельный нормативный акт.
4. Неверный JSON от LLM приводит к понятной обработке ошибки.
5. Недоступный `sc-machine`: LLM не выдаёт юридический вывод по памяти.
6. Недоступный Ollama: baseline продолжает функционировать.
7. Два параллельных запроса не получают чужие результаты.
8. После `docker compose stop` и нового старта аккаунты, история и KB-состояние сохраняются.
9. Гость не изменяет заметки/настройки другого пользователя.
10. Вёрстка и маршруты основных разделов проходят браузерный smoke.
11. Один найденный термин корректно обрабатывается `action_user_request` (регрессия по подозрительному условию `size() > 1`).
12. В материале по образованию/труду/жилью указана редакция/неизвестность актуальности, а не вымышленная дата.

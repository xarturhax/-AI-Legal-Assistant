# Локальный юридический ассистент

Исправление `action_user_request` развёрнуто в рабочем стеке. Агент возвращает понятие
по точному русскому названию. Поиск по части названия доступен через SC-template fallback.
[Разбор и живые проверки](docs/ACTION_USER_REQUEST.md)

Третья опроцентовка проверена на `1868b4b` после редизайна Themis, 11.11.2026.
Новый полный live-набор дал 76 PASS, 1 XFAIL и 0 SKIPPED. Протокол демонстрации
содержит 6 PASS и 1 ошибку релевантности D2, сохранены четыре реальных снимка.
На независимых 21 вопросе ожидаемый источник найден в 3/15 запросов baseline
и 14/15 LLM. Верные отказы составили 6/6 и 4/6 соответственно. Технических ошибок
в 42 выполнениях не было. Эти результаты отделены от исторических 36 вопросов.

Результаты предыдущих этапов описаны в [отчёте проверок](docs/TEST_REPORT.md).
Локальные материалы третьей опроцентовки собраны в `reports/third_review/`.
Все шаблоны и ассеты Themis побайтно сохранены. Пояснительная записка LaTeX
не предоставлена, её обновление и двойная сборка пока NOT TESTED.

Итерация обработки ситуаций добавляет контекст сущностей и явно указанных фактов.
Названия из контекста сопоставляются со словарём текущей OSTIS KB и найденными
источниками. `missing_information` отображается как предложенные моделью вопросы.
Ответ содержит только выдержки из KB, правовая оценка ситуации не выполняется.
Лексическое совпадение не подтверждает обстоятельства пользователя или применимость нормы.

Для общей просьбы о помощи без описания предмета или событий приложение просит
уточнить обстоятельства и возвращает пустую выдачу. Если предмет уже назван,
неизвестные детали допускают частичный поиск вместе с уточняющими вопросами.

При запуске приложение зависит от готовности OSTIS. Ollama необязательна для baseline.
LLM-режим при её недоступности возвращает ошибку с предложением классического поиска.
Недоступность OSTIS приводит к ошибке в обоих режимах.

Исторический прогон после редизайна дал 76 PASS и 1 XFAIL на живом стеке.
Историческая оценка 36 запросов выполнена до Themis в обоих режимах, все 72 выполнения без таймаутов.
Ожидаемый источник найден в 24/30 содержательных запросов baseline и 30/30 с LLM.
Q35 и Q36 возвращают уточнение и пустую выдачу. Все 6 отрицательных случаев LLM
обработала с no_evidence, частичный поиск подтверждён отдельными live E2E.
Работающий сайт отдаёт Themis. Артефакты текущей итерации относятся к испытаниям и документации.
Причины исторического XFAIL и способ исправления описаны в [разборе агента](docs/ACTION_USER_REQUEST.md).

Flask-сайт с юридическим поиском в настоящем **OSTIS/sc-machine 0.10.0** и
интерпретацией русских запросов через **локальный Ollama**. Новая прикладная логика — Python 3.11.
SQLite хранит аккаунты, историю, заметки, календарь и форум. Юридических статей в ней нет.

Форум поддерживает метки, поиск близких формулировок, похожие темы и личные рекомендации
по просмотрам с обратной связью. Это навигация по сообщениям пользователей, без генерации норм права.

**Текущее состояние на 11.11.2026:** подтверждены живые OSTIS и Ollama, поиск с реальными SC-ID,
цепочка Flask → локальная LLM → OSTIS и миграции SQLite. Пользователь подтвердил сохранение

(известное ограничение исходного action_user_request: завершение с пустым результатом).
Переход к поиску шаблонами проверен на реальной KB и отражается в trace.
Сравнение на всех 36 запросах выполнено на живом стеке с Ollama на GPU.
Полная приёмка S0–S7 продолжается.

## Установка на Windows

Нужны Git, Docker Desktop с Linux containers и работающим WSL2, сеть для начальной
загрузки исходников, образов, официального SDK sc-machine и модели. Проверьте требования
[Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/) и
[WSL2](https://docs.docker.com/desktop/features/wsl/). Точная редакция Windows в этой сессии
не установлена: системный запрос получил отказ доступа. Не устанавливайте неподходящую редакцию наугад.

1. Откройте Docker Desktop. `docker info` должен успешно сообщать `OSType: linux`.
2. В каталоге проекта выполните `setup.bat`. Скрипт создаст локальный секрет в `.env`,
   клонирует upstream на зафиксированный SHA с подмодулями, соберёт расширения и исходную KB,
   применит миграции приложения и загрузит `qwen3:4b-instruct`.
3. Выполните `start.bat`. После готовности откроется сайт `http://127.0.0.1:5000`.
4. Остановка: `stop.bat`. База, SC-память и модель остаются в постоянных томах.

Первая установка длительная и требует нескольких ГБ свободного места для модели плюс
места для сборки OSTIS. GPU не обязателен; на CPU обработка LLM может занимать минуты.
Модель задаётся `OLLAMA_MODEL` в `.env`; облачные модели и внешние LLM endpoints отклоняются.
Обычный `start.bat` не скачивает веса и не пересобирает KB.

Если setup обнаружил непустую KB без маркера установки, он сначала сохраняет и проверяет
резервный архив; ошибка бэкапа останавливает повторную сборку.
Повторно вызывать build вручную на существующей KB нельзя: upstream использует `--clear`.
Для осознанной пересборки есть `rebuild-kb.bat`: остановка app/machine, подтверждение `REBUILD`,
tar-копия в `backups/`, проверка архива, затем сборка. При ошибке копирования сборка не начинается.
В обычных скриптах удаления томов нет. Перед переносом системы сохраните также app-data и .env.

## Запуск backend без Docker для разработки

Это позволяет проверить сайт и пользовательские функции. Поиск по-прежнему требует
настоящего sc-server, LLM-режим — настоящего Ollama; отключённые службы дают понятные ошибки.

```powershell
py -3.11 -m venv .venv
.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
.venv\Scripts\python.exe scripts/run_local.py
```

Скрипт использует `.env`, создаёт SQLite в `data/runtime/app.sqlite3` и заменяет Docker-имена
machine/ollama на loopback. В этой сессии проверки выполнены на Python 3.12.6;
Миграции на Python 3.11.14 в Docker подтверждены пользовательским журналом setup.
Порт можно изменить через `APP_PORT`.

## Ollama на NVIDIA в Windows

Docker Desktop передаёт NVIDIA GPU контейнеру через WSL 2. Для включения добавьте
в локальный `.env` строку `COMPOSE_FILE=docker-compose.yml;compose.gpu.yml`.
Обновите запущенную службу Ollama с тем же образом и томом модели:

```powershell
docker compose up -d --no-deps --pull never --wait ollama
```

Выполните запрос в режиме «Локальная LLM», затем запустите
`docker compose exec -T ollama ollama ps`. Столбец `PROCESSOR` показывает долю
модели на CPU и GPU. Для возврата к CPU удалите строку `COMPOSE_FILE` из `.env`
и повторите команду запуска Ollama. [Docker Desktop и GPU](https://docs.docker.com/desktop/features/gpu/)
и [проверка загрузки в Ollama](https://docs.ollama.com/faq#how-can-i-tell-if-my-model-was-loaded-onto-the-gpu).

## Аккаунты и подтверждение по почте

Вход, регистрация, подтверждение и восстановление доступны через меню.
Для отправки через Gmail API включите API в Google Cloud и создайте OAuth-клиент
типа Desktop app. В режиме Testing добавьте Gmail-ящик отправителя в список тестовых
пользователей. Укажите путь к скачанному JSON клиента и подтвердите разрешение на отправку
в браузере под этим аккаунтом. Пароль приложения для OAuth не нужен.
[Инструкция Google Cloud](https://developers.google.com/workspace/gmail/api/quickstart/python)

```powershell
.\.venv\Scripts\python.exe -m pip install google-auth-oauthlib==1.5.0
.\.venv\Scripts\python.exe scripts/configure-gmail-oauth.py "C:\путь\к\client_secret.json"
docker compose up -d --no-deps app
```

Скрипт записывает токен под `data/runtime/mail-credentials/`, вне Git.
Если Google отзовёт или просрочит токен, повторите авторизацию. В режиме Testing
токен обновления для разрешения отправки обычно действует семь дней.
[Срок действия OAuth-токена](https://developers.google.com/identity/protocols/oauth2#expiration)

Если из контейнера доступен SMTP с STARTTLS, можно выбрать пароль приложения Gmail
и выполнить альтернативную настройку. Поле пароля скрыто.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\configure-gmail.ps1
docker compose up -d --no-deps app
```

При регистрации укажите почту получателя. Одноразовый код действует 15 минут.
В списке тестовых пользователей Google нужен ящик отправителя. Получатели кодов
регистрируются в Themis через обычную форму.
Незавершённую регистрацию можно продолжить на странице подтверждения и запросить новый код.
При сбое доставки ошибка показывается на сайте, изменения регистрации или кода откатываются.
Смена пароля отзывает предыдущие сессии. Пароли и коды хранятся в виде хешей.

Для изолированной разработки доступен `DEV_LOCAL_MAIL=1` с пустым `SMTP_HOST`.
Коды остаются в `dev-mail` внутри каталога приложения, в Docker это `/app/data/dev-mail`.
[Справка Google о пароле приложения](https://support.google.com/accounts/answer/185833?hl=ru)

## Поиск и источники

В `/requests` выберите классический поиск или LLM. Кандидаты модели проверяются в SC-памяти;
ответ собирается из извлечённых выдержек. Модель не пишет правовые нормы.
Для точного названия понятия оба режима обычно возвращают один источник: классический
поиск быстрее. LLM предназначена для подбора названия по описанию своими словами.
Перед генерацией приложение читает названия понятий из текущей OSTIS и ограничивает ими
search_terms в JSON Schema; после генерации проверяет выбор ещё раз. Словарь не берётся
из SQLite или оценочного датасета. В результатах LLM показываются выбранные термины.
Сначала вызывается `action_user_request`, затем при пустом/неуспешном результате —
SC-template search, явно отражённый в trace. Таймаут действия не запускает его автоматически повторно.

Справочник `/directory` предлагает поиск по названию и по описанию с локальной LLM.
В обоих режимах карточки понятий извлекаются из SC-памяти напрямую по шаблонам. У источника есть фактический
SC-ID/адрес, title/text links, связанные элементы и неизвестность редакции, если дата не установлена.
Системный SC-ID и числовой адрес различаются; адреса могут измениться после пересборки KB.
Сборщик читает доступные локальные HTML-файлы актов в исходниках и сохраняет текст в SC-ссылках.
Карточка показывает текст и его происхождение. Для отсутствующих файлов отображается статус недоступности.

Общие просьбы без описания события возвращают уточняющий вопрос. Если названо
содержательное событие, приложение может выполнить частичный поиск. Для запросов
о регистрации морских судов приложение проверяет наличие этой темы в текущем словаре
OSTIS. При отсутствии подтверждения оно возвращает `no_evidence` и просит уточнить запрос.
Поля `source_exists`, `source_relevant` и `legal_applicability` описывают наличие записи,
совпадение поискового выражения с названием и применимость нормы соответственно.
Применимость к обстоятельствам пользователя остаётся неизвестной.

Учебное тестирование читает вопросы и разметку из OSTIS, не объявляя их действующим законодательством.

## Документы и новости

Каталог содержит три заполняемых бланка по материалам Национального архива Республики Беларусь
для подтверждения учёбы, запроса сведений о стаже или зарплате и заказа архивного дела.
Встроенные бланки проверяют поля на сервере, показывают заполненный предпросмотр и скачиваются
в DOCX или PDF. Ссылки на опубликованные образцы указаны в карточках.
Для подключения существующего UTF-8 `.txt` добавьте в `data/documents/catalog.json` объект с
полями `id`, `title`, `source_url` (HTTPS), `license`, `file` (относительный путь внутри каталога).
Именованные поля `{{full_name}}` заполняются буквальной заменой, без исполнения Jinja-кода.

RSS-источники задаются владельцем в `NEWS_RSS_URLS` через запятую. Обновление:

```powershell
docker compose exec app python -m app refresh-news
```

Страница `/news` читает последний успешный кеш и показывает источник и время загрузки.
Внешняя публикация открывается в отдельной вкладке, список остаётся открыт.
При отказе сети данные остаются. Для локальной проверки выбрана лента стороннего
трекера публикаций pravo.by. Запустить импорт с этим адресом в уже работающем контейнере
можно через переменную окружения команды.

```powershell
docker compose exec -T -e NEWS_RSS_URLS=https://bielarus.fyi/index.xml app python -m app refresh-news
```

[Описание ленты и источника данных](https://bielarus.fyi/about/).

## Очистка кешей и место на диске

`cleanup.bat` очищает временные профили браузера/тестовые кеши проекта,
неиспользуемый кеш Docker-сборок и кеш скачанных пакетов pip. Образы, контейнеры,
Docker-тома с KB/моделью, SQLite, исходники, .env и установленные Python-пакеты сохраняются.
Команда Docker — [docker builder prune --all --force](https://docs.docker.com/reference/cli/docker/builder/prune/).
Это кеш, который при следующей сборке может понадобиться скачать/создать заново.

Запускайте батник из обычного Windows-сеанса с доступом к Docker Desktop.
В конце показано свободное место на C:, журнал записывается в `logs/cleanup-*.log`.
Файл `docker_data.vhdx` целиком не удаляется: в нём находятся и полезные данные.
Очистка внутри Docker не гарантирует немедленного уменьшения самого VHDX-файла;
принудительное сжатие/выключение WSL этим скриптом не выполняется.

Для отчёта без изменений: `powershell -File scripts/cleanup_space.ps1 -ProjectOnly -ReportOnly`.

## Проверки

```powershell
.venv\Scripts\python.exe -m pytest backend/tests/unit -q
.venv\Scripts\python.exe -m ruff check backend scripts
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/test_manage.ps1
docker compose config --quiet
```

Изолированные проверки с подменами имеют явную метку `mock`. В обычном приложении тестовых источников нет.
Тесты создают отдельный временный каталог на каждый запуск, обходя общий `pytest-of-user`;
постоянный pytest-кеш отключён, поэтому права каталогов предыдущих сеансов не мешают проверке.
Live-тесты по умолчанию SKIPPED. Для настоящего стека:

```powershell
$env:RUN_LIVE_OSTIS='1'
$env:OSTIS_WS_URL='ws://127.0.0.1:8090/ws_json'
$env:OLLAMA_BASE_URL='http://127.0.0.1:11434'
.venv\Scripts\python.exe -m pytest backend/tests/integration -m live_ostis -q
$env:RUN_LIVE_STACK='1'
.venv\Scripts\python.exe -m pytest backend/tests/e2e -m live_stack -q
.venv\Scripts\python.exe scripts/evaluate.py
```

`test_existing_agent_single_title_link` проверяет прямую выдачу `action_user_request`
при одном русском названии. Отдельный live-тест проверяет SC-template fallback
для неполного названия, которое C++-агент не сопоставил.
Последний полный прогон на Windows описан в [отчёте о проверках](docs/TEST_REPORT.md).
Локальный пакет `reports/third_review_final.zip` включает JUnit, результаты обоих
наборов вопросов, скриншоты Themis и процедуру демонстрации.

При недоступной зависимости evaluator пишет `SKIPPED`, `metrics=null` и возвращает exit 2.
Измерить только извлечение кандидатов baseline: `python scripts/evaluate.py --terms-only`.
Набор содержит 36 запросов; аннотации привязаны к исходникам KB, не к действующему законодательству.

Диагностика:

```powershell
docker compose ps
docker compose logs --no-color --tail=100 machine app ollama
curl.exe http://127.0.0.1:5000/health/live
curl.exe http://127.0.0.1:5000/health/ready
```

`live` проверяет процесс. `ready` отдельно показывает database/ostis/llm и даёт 503,
если база или юридическая KB не готовы. В baseline отсутствие модели само по себе не даёт 503.

Если `setup.bat` или `start.bat` завершается с ошибкой, окно остаётся открытым, а полный
журнал записывается в `logs/setup-ДАТА-PID.log` или `logs/start-ДАТА-PID.log`.
В журнале указан этап сбоя. Дождитесь успешного завершения setup до запуска start:
при отсутствии локальных образов start остановится с пояснением вместо попытки их запуска.
Если порт 5000 занят локальным `scripts/run_local.py`, завершите его через Ctrl+C в его терминале
или задайте другой `APP_PORT` в `.env`. Посторонние процессы launcher не останавливает.
Для автоматизированной проверки без паузы на ошибке можно задать `CODEX_NO_PAUSE=1`.

Для debug sc-web: `docker compose -f docker-compose.yml -f compose.debug.yml --profile debug up -d`.
Основной пользовательский вход остаётся один — Flask на порту 5000.

Сборка OSTIS использует `ostis/Dockerfile` и официальный архив SDK sc-machine 0.10.0
с GitHub Releases. Зависимость от Conan-сервера `conan.ostis.net` удалена после подтверждённой
TLS-ошибки. CMake собирает все исходные группы C++-агентов против этого SDK;
`verify_runtime.py` проверяет наличие библиотек, модулей и версию бинарника во время сборки образа.
Подход с `CMAKE_PREFIX_PATH` описан в [документации версии 0.10.0](https://github.com/ostis-ai/sc-machine/blob/4ead42282b7a814edbd352f5f5650f0f4a721141/docs/build/build_system.md#consuming-the-package).
Сборка образа и загрузка юридической KB — отдельные проверки.
Сборщик KB обрабатывает GWF во временной записываемой копии: оригинальные исходники
остаются только для чтения. Если предыдущая установка оставила частичную KB без маркера
готовности, повторный `setup.bat` сначала остановит app/machine, сохранит и проверит её
резервную копию в `backups`, затем повторит сборку. При ошибке бэкапа сборка остановится.

Если после `cleanup.bat` на C: всё ещё мало места: счётчик «кешей проекта» не включает
очистку Docker/pip, их результат находится выше в журнале. Освобождённое место внутри
Docker VHDX может ещё занимать место в Windows. Для переноса хранилища на другой диск
откройте Docker Desktop → Settings → Resources → Advanced → Disk image location,
выберите, например, `D:\DockerDesktop` и примените изменение. Это штатная настройка
[Docker с WSL 2](https://docs.docker.com/desktop/features/wsl/). Самостоятельно удалять VHDX не нужно.
